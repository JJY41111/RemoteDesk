# 快節奏遊戲用途：本機影像延遲基準（2026-09-17）

## 目標與目前結果

使用者以持續接收視窗拖曳一般桌面視窗後，回報畫面「大致穩定」。最終目標
是遠端遊玩《快打旋風》等對輸入延遲敏感的遊戲；目前**尚未**有遠端輸入、
跨電腦連線或 60 fps，不能把穩定的 720p30 當成遊戲體驗已達標。

以 `out\remote_desk_receiver.exe --test` 搭配
`out\remote_desk.exe --network-test` 進行一次五秒本機測試：150 個封包
全部接收、解碼並繪製；150 幀具有效的桌面更新時間戳。QPC 時間戳從
DXGI Desktop Duplication 的 `LastPresentTime`／`LastMouseUpdateTime`
取得，沿編碼封包傳至接收端。封包格式因此升至第 3 版，兩端須使用同次
建置的執行檔。

| 同機階段 | 平均 | P95 |
| --- | ---: | ---: |
| 桌面更新 → 擷取端畫面就緒 | 0.31 ms | 0.35 ms |
| 畫面就緒 → 編碼封包排隊 | 14.55 ms | 15.24 ms |
| 封包排隊 → 接收視窗繪製呼叫完成 | 55.57 ms | 61.79 ms |
| **桌面更新 → 接收視窗繪製呼叫完成** | **70.43 ms** | **76.65 ms** |

最後一項最大值為 95.25 ms。接收後的解碼及 BGRA 轉換平均 54.82 ms，
是這次量測最大的區段；它包含解碼器內部等待，不能直接把全數算成 CPU
轉換時間。傳送端目前仍做 GPU 到 CPU 讀回並在 CPU 上縮放及轉 NV12，
所以 14.55 ms 的擷取後處理也接近 60 fps 的 16.67 ms 幀間隔。

## 如何解讀

Windows 的 [DXGI 幀資訊文件](https://learn.microsoft.com/en-us/windows/win32/api/dxgi1_2/ns-dxgi1_2-dxgi_outdupl_frame_info)
說明這兩種桌面更新時間戳來自 QPC。只統計時間戳有變化、且順序有效的
繪製幀，避免靜止畫面重複編碼把延遲誤算成數秒。本次數字僅能在**同一台
電腦**比較；它仍不包含玩家輸入到遊戲產生畫面的時間、螢幕合成及實體
掃描，也不包含跨電腦網路與遠端輸入回程。因此不是按鍵到畫面的延遲。

目前本機 TCP 串流只綁定 `127.0.0.1`；未做身分驗證與加密，不應直接
開放區域網路或網際網路。要朝遊戲用途前進，先驗證 720p60 的實際幀率及
延遲，再處理 GPU 色彩轉換／硬體編碼、接收端解碼顯示尖峰，以及遠端輸入
和往返延遲。1080p60 是後續目標，尚非實測成果。

## 斷線回歸

先啟動隱藏的本機接收端與持續傳送端，之後刻意終止接收程序；傳送端記錄
`receiver disconnected: send failed (WSA 10054)`，接著記錄停止，
沒有先前的 `fatal`。這驗證的是斷線後收尾，不是自動重連。

原有本機 Loopback 回歸有一次完成 124 幀提交、編碼及解碼，且
`image=yes`；五秒內未維持 150 幀。另一次在桌面無新更新時沒有取得首幀，
自動測試未開始，已手動停止該測試程序。這些現象需在 60 fps 工作前
處理或明確區分測試環境與管線效能；不能宣稱目前穩定 30 fps。
