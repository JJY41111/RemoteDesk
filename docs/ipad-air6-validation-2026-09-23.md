# iPad Air 6（M2）跨設備驗證準備 — 2026-09-23

## 目前狀態

2026-09-24 已由使用者在 iPad Air 6 實機試用，結果與待重測項目見文末。
此前的主機端證據來自同一台 Windows 電腦的 Chrome 和同機 TCP 測試。

## Windows 主機準備

在專案根目錄執行：

```powershell
.\build.bat
cd bridge
npm.cmd ci
npm.cmd run preflight
npm.cmd start -- --host=192.168.1.100 --enable-input --audio --display=0:0
```

`preflight` 會列出本機私人 IPv4 及必要執行檔。此機在 2026-09-23 偵測到
`192.168.1.100`（有線區網）。上面的啟動指令可直接複製；若日後地址變動，
請複製 `preflight` 輸出的整行 `Example:` 指令，勿把說明文字或尖括號貼進
PowerShell。iPad 與主機
要處於可互通的可信任網路。服務只綁指定的 IP；不能用 Tailscale、Hamachi 或
Radmin VPN 的地址冒充實體區網測試。先用
`.\out\remote_desk_input.exe --list-displays` 確認 `--display=0:0` 對應目標螢幕。

第一次可先用 `--720p` 測連線，再移除它測 1080p60。測試時保留 Windows 終端
及主機的停止方式。若防火牆詢問，僅依測試網路的實際信任情況允許私人網路；
不做路由器轉送。

## iPad 設定與連線

1. Safari 開啟主機終端顯示的 `http://<主機 IP>:8442/ca.crt`。對照終端印出的
   CA SHA-256 指紋後，才安裝公開 CA 憑證。憑證私鑰始終留在 `bridge/private/`。
2. 在 iPad 設定中安裝該描述檔，並在「一般 → 關於本機 → 憑證信任設定」開啟
   完整信任。這個 CA 只用於可信任的測試設備；測完可移除。
3. Safari 開啟 `https://<主機 IP>:8443`，輸入主機終端當次顯示的八位配對碼。
   按「播放畫面」，有聲音時再按「播放聲音」。
4. 先以觀看模式確認畫面，再勾「啟用本次遠端操作」。網頁顯示主機確認訊息
   後才會傳送輸入。取消勾選會在主機釋放已按住的鍵與滑鼠按鈕；斷線也會釋放。

## 按順序驗證並記錄

| 項目 | 操作 | 必須記錄 |
| --- | --- | --- |
| 連線 | iPad Safari 配對、播放，斷線後重連 | iPadOS 版本、網路、是否成功、錯誤訊息 |
| 720p60／1080p60 | 各跑至少 10 分鐘，拖曳視窗並快速捲動文字／影片 | 每段結束按「下載測試紀錄」，記 FPS、最長間隔、丟幀、解析度；記主觀糊化及卡頓 |
| 觸控／滑鼠 | 點擊、拖曳、右鍵、滾輪；取消控制時保持一鍵按下 | 座標是否對準、按鍵是否釋放、是否發生誤觸 |
| 鍵盤 | 外接鍵盤方向鍵、字母、功能鍵；網頁文字輸入框測中文 | 各鍵是否到達、焦點與輸入法問題；高權限視窗是否拒絕輸入 |
| 手把 | iPad 配對手把後，在頁面按按鍵、十字鍵與類比方向 | Safari 是否提供 Gamepad API、鍵盤映射是否可用；目前不是 XInput 手把 |
| 音訊 | 主機播放有節奏聲音，iPad 點「播放聲音」 | 有無聲音、破音、明顯不同步；瀏覽器收到 RTP 不等於聽到聲音 |
| 斷線安全 | 控制中關閉 Safari 分頁、斷網、重連 | 主機是否釋放輸入、擷取程序是否退出、是否能重新配對 |

CSV 的每秒 FPS 來自 `requestVideoFrameCallback`；若瀏覽器沒有該 API，退回
`getVideoPlaybackQuality` 的累計影格。最長幀間隔在沒有回呼時留空。這些數字
代表瀏覽器回報，不保證面板真的顯示每張畫面。測遊戲操作延遲可用另一支手機
高幀率錄影，同時拍下手指／按鍵動作與 iPad 畫面變化；不能把不同設備的本機
時鐘直接相減。

## 虛擬延伸螢幕的下一段開發

`--display` 只能擷取 Windows 已存在的顯示輸出。要讓 iPad 成為**新的** Windows
延伸螢幕，需要 Windows Indirect Display Driver（IddCx）及安裝流程；現有
RemoteDesk 沒有這種驅動。本機未找到 `iddcx.h`，目前不能編譯驅動原型。

實作順序：安裝相容的 WDK；從微軟 IddSample 建立獨立驅動實驗專案；先驗證
Windows 能建立、移除虛擬顯示器及 1920×1080@60 模式；再評估該虛擬輸出是否
能由現有 DXGI 擷取管線選到；最後處理 iPad 斷線時的顯示器移除、視窗位置
回復與驅動簽署／安裝。IddSample 的畫面處理只是範例，不能直接當成產品驅動。
參考：[Microsoft IddSample](https://learn.microsoft.com/en-us/samples/microsoft/windows-driver-samples/indirect-display-driver-sample/)、
[Indirect Display Driver Model](https://learn.microsoft.com/en-us/windows-hardware/drivers/display/indirect-display-driver-model-overview)。

針對這些現象已修改程式：

- 畫面邊緣 8 CSS 像素內會對齊到 Windows 螢幕的最外緣，以便觸發自動

  配對，避免畫面無限停在最後一幀。
- 把「已完成的影格間隔」與「目前已停住多久」分開顯示，CSV 另記
  `stalled_ms`。
- 音訊按鈕只在收到音軌後可按；頁面顯示播放狀態、主機音量、主機送出及
  瀏覽器收到的封包數，以便分辨未啟用 `--audio`、主機擷取為靜音與 iPad
  播放問題。舊版 Chrome 測試只能證明收到封包，不能證明有聲音。

下一次 iPad 測試請重新啟動橋接服務，確認指令包含 `--audio`，主機播放
可聽見的音樂並在 iPad 按「播放聲音」。記錄頁面的音訊狀態與測試 CSV；
若再停住，保留主機終端輸出和 `runtime.log`。遊戲可另以 `--720p` 比較
流暢度，但文字細節通常會更少。暫不提高 1080p 位元率，先確定長時間
串流與音訊不再中斷。

橋接服務也會把關鍵斷線原因寫到 `bridge/session.log`（已排除 Git）。
重連會覆寫根目錄的 `runtime.log`，若再發生停頓，先保留這兩份日誌及

解讀為硬體擷取故障，亦不能和新計數直接比較。

last_source_frame_age_ms=18、audio_underruns=4854；沒有證據定位端到端延遲。
測試前 runtime.log 保存在 ipad-runtime-before-timing-fix-2026-09-25.log。

這次修改：

- 影片 sampleTime 改用單調時鐘的經過時間。原本每送一幀只加固定 1/60 秒，
  主機忙碌跳過時段時，媒體時間會落後真實時間。此缺陷已修正，但尚未證明
  它就是這次 iPad 延遲的唯一原因。
- 音訊先累積 40 ms PCM，再開始取用每包 20 ms；供應中斷時重新緩衝。
  超過 120 ms 積壓時保留約 40 ms，裁切維持完整立體聲取樣的 4-byte 對齊。
  新增重新緩衝次數、主機音訊佇列長度和裁掉的樣本數。
- FPS 使用 presentedFrames 累計差值，避免把回呼次數當呈現張數。
  間隔改名為畫面回報間隔，因回呼也會受主執行緒或背景分頁節流影響。
- CSV 加入解碼 FPS、影音接收 jitter buffer 平均等待時間、音訊補償樣本、
  丟包、主機重新緩衝等欄位。接收緩衝以相鄰統計差值計算，並非端到端延遲；
  Safari 未提供的欄位留空。

本機驗證：C++ build 成功；4 個 Node 測試通過（包含不規則 PCM 批次與
