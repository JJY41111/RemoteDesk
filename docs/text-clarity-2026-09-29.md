# iPad 文字清晰度更新（2026-09-29）

## 2026-09-29 實機回饋與新版

使用者已確認 150% 檢視放大沒有讓細字變清晰。新版擷取日誌確認 `--display=0:0` 來源實際為 2560×1440，之前固定轉成 1920×1080。現可於配對時選原生 2560×1440 模式，保留來源像素；預設仍是遊戲優先的 1080p。原生模式在本機 Chrome 已收到 2560×1440 畫面，但 iPad Safari 的字體與遊戲表現尚未驗證。完整數據及操作步驟見 `docs/performance-quality-2026-09-29.md`。以下為上一輪紀錄，來源尺寸推測與「待試放大」部分已由本節取代。

## 問題與處理

目前主機傳送的是 1920×1080。Windows 現在列出的其中一個螢幕為 2048×1152，但尚未證明它就是 `--display=0:0` 擷取的來源，不能據此量化主機縮圖。舊網頁另外把完整 1080p 畫面壓入最多 1200 CSS 像素寬、77vh 高的區域。遠端細字在平板上因此很小。這些資料能指出顯示縮小，但不能單憑它們判定編碼損失有多大。

接收端已移除 1200 CSS 像素的頁面寬度上限，增加「放大文字 150%」和「移動畫面」。放大時只改變畫面的檢視大小，不降低傳送解析度，也不更動編碼、影音同步或接收緩衝。先按「移動畫面」可拖到想看的位置，再按「返回遠端操作」繼續使用滑鼠；滑鼠座標仍映射到整張 Windows 桌面。顯示列會列出實際收到的影像解析度。

## 本機驗證

- `node --check bridge/web/app.js` 通過。
- `bridge` 內 `npm.cmd test`：11 項通過。
- `bridge` 內 `npm.cmd run test:ui`：以 1180×820 CSS 像素、2 倍像素密度模擬平板橫向大小；檢查 150% 放大、拖曳捲動、放大後座標與底部邊界、既有輸入與音訊介面，通過。這使用 Chrome，不是 iPad Safari。
- 主機編碼與傳輸程式未修改，故未重編譯或重跑網路長測試。現有服務無須重啟，iPad 重新整理網頁即可取得新版介面。

## 下一次實機驗收

在同一段有小字的畫面，分別看「完整畫面」與「放大文字 150%」。若放大後文字可讀，主要是縮小顯示所致；若放大後筆畫本身仍糊或破碎，再針對主機縮圖取樣、H.264 編碼或 Safari 呈現進一步量測。請同時確認顯示列為 1920×1080，並試一次放大後的滑鼠定位。完整畫面與放大畫面截圖、主機同畫面截圖最能定位剩餘問題。
