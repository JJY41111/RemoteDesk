# 本機預覽延遲診斷（2026-09-16）

## 問題與修正

使用者觀看 720p／30 fps 的本機 TCP 接收視窗時，感覺到明顯延遲。
在封包排入傳送佇列、接收完整封包、解碼轉換完成及視窗 `WM_PAINT` 完成處
加入 QPC 時間戳後，首輪五秒測試顯示耗時主要在接收端解碼／色彩轉換階段，
不是本機 TCP 傳送。

Microsoft H.264 Decoder MFT 的 `CODECAPI_AVLowLatencyMode` 使用 `VT_UI4`
值 `1`。先前網路接收端沒有設定此模式；Loopback 解碼器曾以 `VT_BOOL`
嘗試設定，類型不符合該解碼器要求。現在接收端在協商媒體格式前設定並記錄
設定是否成功；Loopback 解碼器也改用正確類型。若設定失敗，程式仍可運作，
但日誌會顯示 `low_latency=no`。設定類型依據
[Microsoft `CODECAPI_AVLowLatencyMode` 文件](https://learn.microsoft.com/en-us/windows/win32/medfound/codecapi-avlowlatencymode)。

## 五秒測試結果

每次執行 `build.bat`，先開 `out\remote_desk_receiver.exe --test`，再開
`out\remote_desk.exe --network-test`。結果取自 `receiver.log`。修正後另重跑
兩次，以確認末幀繪製、固定大小統計視窗與時間戳追蹤的調整。桌面內容會變，這不是嚴格控制
變因的效能基準測試。

| 測試 | 接收／解碼／實際繪製 | 傳送佇列＋本機網路平均 | 接收後解碼＋轉換平均 | 封包至繪製平均 | P95 | 最大 |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| 修正前 | 150／150／150 | 0.26 ms | 1175.40 ms | 1176.47 ms | 1259.60 ms | 1284.83 ms |
| 修正後首輪 | 150／150／149 | 0.14 ms | 54.55 ms | 55.57 ms | 62.30 ms | 69.23 ms |
| 修正後再驗 | 150／150／150 | 1.00 ms | 57.27 ms | 59.13 ms | 80.07 ms | 100.72 ms |
| 最終回歸 | 150／150／150 | 0.41 ms | 55.50 ms | 56.88 ms | 69.01 ms | 109.57 ms |

首輪修正後少計一次視窗繪製；測試模式當時收到串流結束就立即關窗，
可能讓最後一幀來不及繪製。接收和解碼仍各完成 150 幀。
再驗時先強制繪製最後一幀再關窗，
150 幀均完成繪製與時間戳配對。兩次修正後測試均回報 `low_latency=yes`。

原有功能回歸：`--loopback-test` 完成 150 幀編碼及 150 幀解碼；
`--record-test` 完成 150 幀錄影。

## 量測邊界與下一步

這裡的「封包至繪製」從**已編碼封包排入傳送佇列**開始，到接收視窗
`EndPaint` 後取樣為止，包含本機網路、接收端解碼與 BGRA 轉換、UI 排程
及 CPU 繪製呼叫。它**不包含**桌面擷取、縮放／色彩轉換、編碼、桌面合成器
與實體螢幕掃描，因此不是滑鼠動作到螢幕顯示的端到端延遲。
接收端僅保留最近 1800 個有效繪製樣本供結束時統計，避免長時間執行時
量測資料持續增長；本文件的五秒測試都未觸及此上限。

QPC 時間戳只在**同一台電腦的兩個程序**之間比較；跨電腦測量需要時鐘同步
或其他方法（參見 [Microsoft QPC 文件](https://learn.microsoft.com/en-us/windows/win32/sysinfo/acquiring-high-resolution-time-stamps)）。目前也沒有長時間、跨電腦、1080p60、壅塞或遊戲互動的證據。
接下來應先由使用者手動確認體感，再量測擷取到編碼的時間，並處理佇列壅塞
及安全連線；未加入身分驗證／加密前，不應開放區域網路。
