`video_jitter_buffer_ms` 是 WebRTC 封包進入 iPad 接收緩衝到影格離開緩衝的時間；
它不包含手把、遊戲運算、Windows 擷取、編碼、網路傳送、解碼與螢幕顯示全部時間。
`worst_gap_ms` 是瀏覽器畫面回報間隔；這份 CSV 不足以判定停頓起因。
使用者主要回報的是主機螢幕和 iPad 畫面持續不同步，並非一直停格。
視訊接收緩衝中位數 146 ms 只涵蓋 iPad 接收端的一段，不能當作完整畫面延遲。

已將手把狀態變更改為下一個瀏覽器畫面週期立即送出，取消原本至少 32 ms 的節流等待。
頁面新增可關閉的「低延遲模式（測試）」：若 Safari 支援 `RTCRtpReceiver.jitterBufferTarget`，
會對音訊與視訊要求最短接收緩衝。此值只是瀏覽器的目標，不保證實際延遲，
也可能增加卡頓。新版 CSV 另記錄視訊目標及網路下限，以辨別緩衝來源。

下一輪在同一 Wi-Fi、同一遊戲畫面各測至少兩分鐘，下載 CSV：

1. 1080p，低延遲模式關閉（基準）。
2. 1080p，低延遲模式開啟。若 Safari 顯示不支援，記錄訊息即可。
3. 重啟主機加 `--720p`（1280×720，約 8 Mb/s），重做關閉與開啟測試。

比較視訊接收緩衝、FPS、最長畫面間隔及實際操作感。真正的按鍵到畫面延遲
仍須用同一段慢動作影片同時拍到 iPad 手把按下與 iPad 畫面反應，才能估計。

`docs/latency-display.html`，將主機螢幕與 iPad 畫面同時拍進照片，讀取兩邊時鐘差。
多拍幾張，可分辨固定延遲與偶發停頓；這個差值仍不含手把到遊戲畫面的反應時間。

時鐘只顯示整秒、影片只涵蓋 10 秒，無法從中判斷使用數分鐘後延遲是否累積，

## 原生 iPad App 路線

使用者確認 Safari 顯示「此版 Safari 未提供接收緩衝控制」，故原網頁的
`jitterBufferTarget`／`playoutDelayHint` 開關不能用來降低這台 iPad 的緩衝。
已建立 `ipad/RemoteDesk.swiftpm`，以 SwiftUI、原生 WebRTC SDK、
GameController 和 UIKit 接入既有 bridge 協定，避免提供未生效的同名開關。
Windows bridge 增加原生 WebSocket 握手識別，仍保留 TLS、配對碼及遠端操作授權。
網頁端在接收器不支援或僅部分支援緩衝控制時，會停用無法生效的開關；
完整支援的瀏覽器仍可使用原實驗開關。
目前沒有 Mac/Xcode；待 iPad Swift Playgrounds 實際載入套件、編譯並運行後，
才能判斷這條路是否可用，也不能預設原生 WebRTC 一定比 Safari 低延遲。

## 9 月 29 日：恢復網頁版並確定優先順序

原生 App 在 iPad Swift Playgrounds 上於首個畫面出現前當機；不含 WebRTC 的
最小 App 解壓後開啟仍轉圈，尚無可比較的原生效能數據。先以已經過 iPad
實機測試的 Safari 網頁版為主，繼續量測並降低延遲。這是目前的開發優先順序，
不是斷言 Safari 一定比原生 App 快。

網頁版一度在配對後失效，查到 `bridge/server.mjs` 的 WebSocket `connection`
事件未傳入升級請求 `req`，但配對完成的日誌程式讀取 `req.headers`，使
Node 程序直接拋錯退出。已把 `req` 傳給事件處理器；Windows 本機已用實際
WebSocket 配對確認收到 `paired`，測試連線關閉後 HTTPS 首頁仍回 HTTP 200。
這只證實主機端，不等於 iPad Safari 已恢復；須由 iPad 重試確認。
由工具啟動的後續 bridge 程序又在約三分鐘後退出，未留下 JavaScript 錯誤或
Windows Application 當機事件；目前無法區分工具工作階段結束與應用程式自行退出。
新增 `bridge/start-ipad.cmd` 供使用者在自己的視窗啟動並保留主控台輸出。

使用者後續已確認成功連線。9/29 新版低延遲模式改為主機傳送 RTP 播放
延遲目標及調整音訊排隊上限，取代本文先前記錄的 JavaScript API 開關。
實作、測試及 iPad 驗證方式見 [新版說明](web-low-latency-2026-09-29.md)。
