# Safari 27 接收緩衝驗收版

接收端版本 2026-10-04.3。加入主畫面的PWA仍為主路線；不重建原生App。Apple Safari 27說明列出RTCRtpReceiver.jitterBufferTarget，但以實機每條音軌／視軌的API能力為準，不依OS字串宣稱支援。

## 本次更新

- 「功能 → 縮短排隊延遲」偵測畫面接收能力，新增80／120／160 ms畫面基準選擇；勾選預設關閉，每次重新配對不自動套用。只有勾選且支援才可選目標。
- 實測目標緩衝缺少時，以實際jitterBufferDelay統計判斷過高緩衝。兩者皆缺少則等待，不假裝已生效。
- 原本緩衝已低時不抬高到80 ms。介入後隨RTT與網路最低緩衝上調，不再使用可能低於網路下限的240／300 ms硬上限。選項為基準，不保證實際緩衝或端到端延遲等於该值。
- 讀回接受值，畫面／音訊分别顯示。不支援或寫入失敗顯示原因，不宣稱降低延遲。關閉回寫null以還原瀏覽器預設。
- 持續解碼但前景畫面2.5秒未呈現時還原；必須有最近5秒內有效接收統計。安全阻擋避免舊主機確認訊息再次套用，使用者再次手動勾選才重新嘗試。還原失敗會顯示設定錯誤。
- 沿用主機音訊60／120 ms排隊切換，不新增RTP playout-delay擴充，不使用曾使iPad凍結的0–50 ms目標。解析度、碼率策略、FPS與輸入傳輸不變。
- CSV追加音訊接收控制支援、畫面基準、還原次數、安全阻擋及設定錯誤數；原欄位順序保留。

## iPad驗收步驟

1. 更新iPadOS後關閉並重新開啟PWA，功能選單確認版本2026-10-04.3。
2. 同場景先保持未勾選約2分鐘，下載CSV作基準。
3. 勾選縮短排隊延遲，先測80 ms約2分鐘；讀取狀態是否支援、瀏覽器是否接受，下載CSV。
4. 若音訊破裂或畫面不穩，改120 ms，同場景比較；也可隨時取消勾選還原。若原本緩衝已低而維持預設，不表示按鈕失效。
5. 比較呈現FPS／最長間隔、實際接收緩衝、RTT、失包、還原及錯誤數和操作聽感，不能只比較要求值。

## 驗證範圍

37項Node測試與iPad尺寸Chrome介面回歸通過，包含缺少目標統計、低緩衝不抬高、網路最低值超過舊硬上限、目標選擇及停止呈現還原。不是Safari實機驗收。

隔離埠15秒真正DXGI／H.264／Chrome WebRTC測試，開啟並寫入80 ms，持續播放後關閉還原null。高缓衝分支以注入統計觸發，不是實際限速或失包；API寫入與還原使用真正RTCRtpReceiver。解碼1064幀、bridge丟棄0、瀏覽器累計丟棄41幀、最後視訊接收緩衝12 ms；不以此宣稱低延遲改善或零丟幀。結果quality-1080-gpu-receiver-control-tailnet-server-15s.json。兩個正式服務的HTML／JS從磁碟即時提供，無需重啟；使用者仍須重新開啟PWA才能載入新程式。
