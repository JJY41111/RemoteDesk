# PWA 畫質修正：2026-10-04.1

## 使用者資料與原因

來源為 `remotedesk-metrics-2026-10-04T08-39-16-192Z.csv`，708 筆，約 11 分 47 秒。
本次 video_mode 全程為 1080p，有效解析度均為 1920×1080；先前 10-02 07:15 覺得文字清楚的紀錄為原生 2560×1440。放大 150% 只改顯示大小，不增加串流像素，不能補回文字細節。

排除前五秒後，主機送出平均約 60 FPS、iPad 呈現約 58 FPS。WAN 目標碼率平均約 3.87 Mbps、最低 2.2 Mbps；實際輸入碼率平均約 4.63 Mbps，不能將目標當成瞬時硬上限。CSV 亦有真實突發失包與最長 2234 ms 畫面回報間隔，不能只靠提高碼率處理所有卡頓。

檢查控制器確認：舊版除了新增失包，亦會單凭 NACK 次數降碼率；這份資料出現失包增量為零卻繼續降碼率。NACK 是重傳要求，不能直接當作尚未補回的封包數。另 packetsLost 因遲到封包下降時，舊版重設乾淨樣本計數，延後畫質恢復。

## 修改

- 只依新增失包比例觸發原有 15%／30% 碼率降低，不再單依 NACK 次數降低。
- 遲到封包補回不再被當作新工作階段；無新增失包時可正常累計恢復樣本。
- 三個乾淨回報後逐步恢復碼率，每次約 10%、至少 300 kbps，仍遵守 8 Mbps／低流量模式 5 Mbps 上限與 2.2 Mbps 下限。沒有直接固定高碼率。
- 記住使用者選擇的畫面模式；未知或失效選項回到原預設 1080p。首次仍使用既有遊戲優先模式，沒有自動增加解析度與負載。
- 接收端版本 2026-10-04.1。WAN 控制器需重啟 9443 才生效；前端需關閉重開或重載。

## 驗證範圍

六項碼率測試通過，含真實失包降速、零失包大量 NACK 不降速、遲到封包恢復、上限與無效回報。app.js 語法與現有 iPad 尺寸 UI 回歸通過；實際來源頁面重新載入後保留 native 選項的瀏覽器測試通過。

隔離連接埠 8544／55444 的實際 Windows 擷取、H.264 與 Chrome WebRTC 動態碼率測試用於確認傳輸未被修正破壞。這些測試不是 iPad 畫質或行動數據驗收。

測試已通過：模擬失包讓編碼器套用 8→5.6 Mbps，乾淨回報後回升到 6.1 Mbps；解碼 1031 幀，主機送出約 59.4 FPS、bridge 丟棄 0 幀，鍵鼠快通道仍開啟。結果保存於 bridge/test-results 的 quality-1080-gpu-tailnet-server 檔案。

確認無擷取工作階段後重啟 9443 套用控制器；8443 未重啟。前端版本更新需使用者關閉重開 PWA。

待驗收：同一場景的新 iPad CSV、文字截圖和移動畫質；確認碼率恢復是否造成重複壅塞。文字用途請選一次「原生 2560×1440」，新版會記住；遊戲可維持原 1080p。不能宣稱所有畫面模糊或失包已消除。
