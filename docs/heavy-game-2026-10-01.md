# 2026-10-01 重負載遊戲可選模式

## 依據與範圍

使用者提供的 `remotedesk-metrics-2026-09-30T15-54-06-389Z.csv` 共 641 筆，約 10 分 40 秒。預設 1080p 串流有長段接近 60 FPS，也有主機送出降至約 20–30 FPS、GPU 讀回年齡升高的時段；另有主機仍送約 60 FPS 而 iPad 出現突發視訊遺失與呈現下降的時段。CSV 未標記遊戲切換秒數，不能把各段直接歸屬某一款遊戲。主機同場次紀錄為 `bridge/test-results/session-2026-09-30T15-44-16-876Z-gpu1080.log`。

使用者回報 CPU 轉色比較模式不如原本的 1080p 遊戲優先；主機 CPU 紀錄約 71 秒的平均編碼 43 FPS、轉色平均 29.5 ms（最高 130.2 ms）。兩次場景未必相同，不能當嚴格同場景 A/B，但沒有理由把 CPU 模式設為預設。

## 本次處理

- 保留 `1080p：遊戲優先` 為配對頁預設、60 FPS、16 Mbps；不改既有輸入、音訊或 WebRTC 播放設定。
- 配對頁新增可選 `1080p：重負載測試（30 FPS）`，主機維持 1920×1080，以 GPU 轉色，改以 30 FPS、10 Mbps 編碼。CPU 模式仍可供開發診斷，但不再顯示於一般配對選項。
- 協定的 C++ 發送端與 Node 接收端均允許 1920×1080@30；增加相應單元測試。CSV 的 `video_mode` 可區分 `stable1080` 與原本 `1080p`，每次斷線後另封存 `session-*-stable1080.log`。
- 此模式是同解析度的可選折衷：若 GPU 與網路負載下降，可能減少部分尖峰，但 30 FPS 本身的動態流暢度低於 60 FPS，且不能救回 DXGI 僅更新 10 FPS 的遊戲畫面。尚無 iPad 實機驗證。

## 驗證

第一次隔離測試發現舊協定不接受 1080p30，主機顯示 `Invalid TCP H.264 packet`；已同步修正 C++ 與 Node 驗證，重新編譯並重測。

| Windows 隔離埠實測 | 觀察 |
| --- | --- |
| 可選重負載模式，約 12 秒 | 1920×1080@30；bridge 末秒約 29.7 FPS、累計丟棄 0，Chrome 約 30 FPS、接收緩衝 10 ms、視訊遺失 0 |
| 原本預設模式，約 12 秒 | 1920×1080@60；bridge 末秒約 60.4 FPS、累計丟棄 0，Chrome 末秒約 58 FPS、接收緩衝 10 ms、視訊遺失 0 |

編譯成功，13 項 Node 單元測試及 iPad 尺寸 Chrome UI 測試通過。隔離測試使用 8544/55444；原 8443/5000 服務仍在，未重啟或中斷。這些是 Windows 靜態桌面測試，不能證明《蜘蛛人 2》或《猛獸派對》會改善，也不能據此聲稱快打、地平線的 iPad 表現完全無退步。

## 實機驗收

使用者下次方便時重新啟動原 bridge，分別以相同遊戲、相同場景、相同主機圖形設定與 iPad 網路，測預設 `1080p：遊戲優先` 和新 `1080p：重負載測試（30 FPS）` 各至少兩分鐘，下載兩份 CSV。重點比對主機擷取更新、送出、iPad 呈現、視訊遺失、最大畫面間隔與操作感受。若重負載模式只是把 60 FPS 場景降到 30 FPS、卡頓未改善，就撤回它；若能明顯降低尖峰，再考慮細化為 45 FPS 或動態調整，先保留預設不變。
